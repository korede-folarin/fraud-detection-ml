Fraud Detection.

A fraud model built to UK bank model-validation practice, with a plain-English reason for every declined payment.

The score is not the interesting part. The judgement calls are: why the leaderboard winner was not chosen, where the cost-optimal threshold broke on later data, and what the explanations can and cannot tell a customer.

Judgement

The reasons are faithful to the model, but on this dataset most of them are anonymised components, so the customer learns that a reason exists, not what it is. That is a limit of the data, not the method: with a bank's named features the same code would name them. I chose honest-but-vague over inventing plausible meanings, because a notice that misdescribes the model is worse than one that says little.

The false alarm is the case to look at. It is declined with confident-sounding reasons and is wrong. That is why the notice says the decision is automated and offers a manual review: the explanation describes the model, it does not prove it right.

02 · Threshold & cost

Where to draw the line

A missed fraud and a false alarm do not cost the same, so the threshold is set by expected cost, not F1. It was chosen on the validate set and then frozen before the test set was scored.

Judgement

Choosing the threshold on the test set would have produced a better-looking number and a meaningless one, so it was fixed on validate first. The costs are assumptions, not measured figures, and the optimal threshold depends only on their ratio. A bank would agree that ratio with its fraud-operations and complaints teams before trusting the optimiser.
